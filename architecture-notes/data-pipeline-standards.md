# Data Pipeline Architecture — Industry Standards Check (Sept 2026)

Scope note: this checks the plan against *current* practice for solo/small-scale heterogeneous-source ingestion, without re-deriving the internal reading list (medallion architecture, Singer discover/read(state)/emit contract, hexagonal ports-and-adapters, Airbyte CDK/Meltano as reference shape, Splink/dedupe for probabilistic ER, Dagster software-defined-assets concept, transactional outbox for `matches.status`, and per-source freshness/zero-row alerting). Those are assumed as background, not repeated here except where they need refining.

## Entity resolution at small scale

**Domain-as-canonical-key + normalized-name-fallback is consistent with current practice, and is in fact the commonly recommended middle ground** — not a corner-cutting compromise. The 2026 literature on this is fairly consistent: full probabilistic record linkage (Splink, `dedupe`, Zingg) is aimed at datasets where you have enough volume to fit a Fellegi-Sunter model or enough labeled pairs to train a classifier — sources repeatedly frame Splink as designed for "millions of records" and note that `dedupe` explicitly "does not scale well" but also implies real setup and tuning cost that isn't justified below that scale. For 2-10 sources and low request volume, that machinery buys little: no training pairs, no meaningful class imbalance to model, and no throughput problem to solve.

The middle ground that's actually recommended between "exact match" and "full probabilistic model" is a **deterministic multi-stage pipeline**, which is what a domain-key + fuzzy-name fallback already approximates:

1. **Blocking/canonical key first**: domain (registrable domain, normalized — strip `www.`, protocol, trailing slash, lowercase) is exactly the kind of high-precision deterministic key this approach recommends leading with, because it's cheap and nearly unambiguous for a company entity.
2. **Normalization before any fuzzy comparison**: lowercase, strip punctuation, strip legal suffixes (Inc., LLC, Ltd., Corp., Co., GmbH, S.A., etc. — pull the suffix list from something like OpenSanctions' reference data rather than hand-rolling one), collapse whitespace. This step alone resolves a large fraction of near-duplicates before any distance metric runs.
3. **Token-aware fuzzy fallback**: for names that survive normalization without matching, current guidance is to layer methods rather than pick one — **Jaro-Winkler** for short name-like strings (it rewards shared prefixes and handles transpositions, and is generally regarded as the strongest single metric for this), with **Jaccard/token-set overlap** for multi-word names where word order varies ("Acme Robotics" vs "Robotics Acme Inc"). Concrete thresholds cited in current sources: Jaro-Winkler ≥ ~0.92 for auto-match, ~0.85–0.92 as a manual-review band, below that treat as no-match. These are heuristic starting points to tune against your own false-positive tolerance, not universal constants.
4. **Phonetic matching (Soundex/NYSIIS/Metaphone) is a blocking aid, not a scorer** — current practice pairs a phonetic key for *candidate generation* (cheaply grouping likely-similar names before doing pairwise comparison) with a character-based metric for the actual match decision. At 2-10 sources you likely don't need this step at all — the corpus is small enough to brute-force compare candidates.
5. **A known caveat worth internalizing**: normalization only fixes legal-form noise (Ltd/GmbH/Inc). It does *not* disambiguate meaningful business words like "Group," "Holdings," "Labs," or "AI" that carry real distinguishing signal — don't strip those, and expect them to occasionally cause both false positives (same base name, different entity) and false negatives (same entity, inconsistent branding across sources).

Practical recommendation: keep the domain-key-first approach, formalize the fallback as normalize → legal-suffix-strip → Jaro-Winkler + token-Jaccard with the thresholds above, route the ambiguous middle band to a manual-review queue (a row in Postgres you occasionally eyeball) rather than auto-deciding it, and only reach for Splink/`dedupe` if/when you accumulate enough manually-adjudicated pairs to make training worthwhile — which, realistically, is a "someday" trigger, not a launch requirement.

## Idempotent/incremental ingestion without a source-provided cursor

Current practice for sources with no native cursor (Algolia-backed directories with no `updated_at`, HTML scraping) converges on **content hashing as the de facto watermark substitute**, layered with a coarse recrawl schedule:

- **Hash the extracted/normalized fields, not raw HTML.** Guidance is consistent that hashing raw markup is noisy — ads, view counters, CSRF tokens, and timestamp-on-every-load fields change on every fetch and would make every row look "changed." Extract the fields you actually care about into a normalized JSON shape first, hash that (SHA-256 is the default choice), and store the hash keyed by your own stable identifier (e.g., normalized domain or source-native ID if one exists) plus a `seen_at`/`changed_at` timestamp. Compare the new hash to the last stored one; only emit a row downstream when it changes. This is effectively "the cursor the source doesn't give you" — self-generated content-addressed state instead of an external bookmark, which fits directly into the existing Singer-style state/bookmark model: the "cursor" for these sources is just `(id, content_hash)` instead of `(id, updated_at)`.
- **Tiered recrawl cadence rather than one fixed interval.** A recommended pattern is a full/baseline sweep on a slow cadence (e.g., weekly) to catch anything that fell out of "new" listings or pagination, plus a faster incremental check on a tighter cadence for the pages/entries most likely to have fresh signal (e.g., "new" or "recently updated" sort orders on a directory, RSS feed's own recency ordering). This matters specifically for something like an Algolia-backed directory: you can usually query it sorted by a recency-ish facet (createdAt, or an internal ranking) even without a public "give me only what changed since X" endpoint — treat "first N by recency sort" as your pseudo-cursor and rely on the content hash to catch the rest.
- **For the Algolia case specifically**: this is a well-documented gray area, not a novel problem. Directories built on Algolia routinely expose the app-ID and search-only API key in their frontend JS (that's how the client-side search widget works) — recent write-ups walk through extracting the app-ID/API-key pair via regex over page source and then querying the Algolia Search API endpoint directly with the same filters/facets the UI uses. This is more stable than scraping rendered HTML (you get structured JSON back) and doesn't require a headless browser. It's still an *unofficial* integration — the key is a search-only key, not an admin key, and the practice is treated as normal "inspect the network tab" behavior rather than exotic reverse-engineering, but it is coupled to that site's frontend implementation and can break without notice, so it still needs the same schema-drift/zero-row detection as everything else (see below).
- **Idempotency at the write side, unchanged from standard advice**: upsert on `(source, source_native_id)` or `(source, canonical_key)`, and let the content-hash comparison be what decides whether to touch `updated_at`/re-trigger downstream scoring — a re-fetch that hashes identical should be a no-op write, not a new "change" event. This keeps the incremental design idempotent even if a run is retried or double-scheduled.

This is a refinement, not a change: it fits inside the existing Singer-style discover/read(state)/emit contract, it just specifies that for cursor-less sources, "state" is a per-entity content hash map instead of a scalar high-watermark, and that recrawl cadence is itself part of the per-source config.

## Orchestration at solo scale

**Cron + a job_runs table is still the sensible, current default for 2-10 scheduled pulls/day**, and current comparisons of the "modern" alternatives reinforce rather than undercut this:

- **Dagster** got *more* expensive to adopt at solo scale during 2026, not less: as of May 2026, Dagster+ removed the included credits from its Solo/Starter plans and moved to per-asset-materialization billing with no free allowance. Combined with Dagster's steeper conceptual surface (software-defined assets, resources, sensors) being explicitly aimed at teams wanting asset lineage, this makes self-hosted OSS Dagster (still free) usable but heavier than needed for this scale, and Dagster+ actively worse-suited than it was a year prior. The "software-defined-assets concept, read for shape" framing in the existing plan holds — don't run it.
- **Prefect** is consistently the tool current comparisons point to for solo/Python-first use if you outgrow bare cron: it wraps plain Python functions/decorators rather than requiring a DAG-definition framework, has a lighter local dev loop, and its OSS server is self-hostable for free (Prefect Cloud is the paid layer, not required). If you ever want retries-with-backoff, a run-history UI, and alerting without hand-rolling them into your `job_runs` table, Prefect is the documented next step up — but it's an upgrade path, not a launch requirement.
- **A genuinely new-in-2026 option worth naming**: GitHub Actions `schedule:` triggers are now frequently cited as *the* default lightweight cron for solo/hobby data pipelines specifically because they're free (2,000 min/month on private repos, unlimited on public), require no server of your own to keep alive, and the workflow YAML doubles as your deployment mechanism. Caveats that show up consistently: UTC-only scheduling, best-effort (not exact) trigger timing under load, and workflows auto-disable after 60 days of repo inactivity — all fine for a "handful of runs per day" personal project but worth knowing about before relying on it for anything latency-sensitive. This is a reasonable substitute for "cron" if you don't want to keep a machine running, while keeping the same job_runs-table-as-source-of-truth design.

Net: no change to the core decision. The refinement is (a) explicitly rule out Dagster+ for cost reasons rather than just complexity reasons, and (b) note GitHub Actions' `schedule:` as a legitimate zero-infrastructure implementation of "cron" if there's no always-on machine, with Prefect OSS named as the specific, current, self-hostable escape hatch if the job_runs table ever stops being enough.

## Lightweight data-quality/observability

Great Expectations remains the enterprise-scale default that current sources agree is overkill here, but two lighter, current, real alternatives cover the specific failure modes the plan cares about (zero-row runs, schema drift):

- **Pandera** is the closest match for **schema drift detection** specifically. It's a Python-native, dataframe-oriented validation library (works over pandas, and by 2026 also Polars/Dask/PySpark/Ibis backends under one schema definition) that lets you declare expected columns/dtypes/simple statistical constraints as code, integrated with type hints. Current write-ups frame its core value proposition almost exactly as the plan's use case: "if a third-party feed changes its schema without warning, Pandera catches the discrepancy before it corrupts downstream data." For a solo project already writing Python ingestion adapters, this is a much lower-ceremony fit than Great Expectations' suite/checkpoint/datasource object model — it's closer to "assert this looks like what I expect" inline in the adapter code.
- **Soda Core** is the closest match for **run-level / freshness-style checks** (row counts, null rates, freshness thresholds) if you want checks declared outside Python, in YAML, independent of any single language. It's explicitly positioned in 2026 comparisons as the lightweight, SQL/YAML-native alternative to Great Expectations, free and OSS at the Core tier, fast to drop into an existing pipeline without adopting a full framework.
- **Elementary** is worth knowing about but is a poorer fit here specifically because it's dbt-native — it derives its freshness/volume/schema anomaly detection from dbt's manifest and run metadata. If a dbt layer ever gets introduced for the silver/gold transforms, Elementary becomes a strong, current, OSS option for "detect zero-row runs and schema drift" with very little config (it surfaces `freshness_anomalies`/`event_freshness_anomalies` out of the box). Without dbt in the stack, it's not applicable — don't add dbt just to get it.
- **For the specific zero-row-is-a-bug idea already in the plan**: none of these tools replace the recommended design (per-source last-successful-row timestamp + alert at 2x expected cadence) — they're complementary. Pandera/Soda checks run *inside* a job to fail it loudly (schema mismatch, empty result set at parse time); the freshness/cadence table is the *outside* view that catches "the job silently stopped running at all," which a schema check alone can't. Current practice treats these as two different layers of the same discipline, not competing solutions.

Recommendation: adopt Pandera for per-adapter schema assertions (cheap, Python-native, fits the ports-and-adapters seams naturally — one schema per SourcePort's output shape) and keep the freshness/cadence table as the run-level observability layer. Soda Core is optional — reach for it only if checks need to live outside Python or be shared with something non-Python later. Skip Great Expectations and skip Elementary unless dbt gets adopted for transforms.

## What's new or changed recently

- **`dlt` (dlthub) has become the practical successor to hand-rolled Singer taps for small/solo Python ingestion**, and is worth a closer look than "read Singer for the contract shape." Where Singer defines a spec that Meltano/Airbyte implement as heavyweight tap/target processes, dlt is a plain importable Python library — you write a generator function, decorate it, and get schema inference, incremental-loading primitives (including cursor/state management matching the Singer bookmark concept), and warehouse loading without adopting a separate orchestration framework or subprocess-based tap protocol. Sources note explosive adoption through 2026 (reported ~81,000 pipelines by January 2026), including a notable shift toward AI-agent-authored pipelines using it, which is itself a signal the API is simple enough to be a good target for codegen. For this project, dlt is a plausible concrete implementation for the "N adapters behind one SourcePort" idea — it wouldn't replace the ports-and-adapters architecture, but individual adapters (especially the official-JSON-API one) could be thin wrappers around a dlt source instead of fully hand-rolled HTTP/pagination/retry code.
- **LLM-based extraction is now a real (if narrow) option for the HTML-scraping source(s)**, not just a novelty. Current 2026 guidance from scraping-tooling vendors is consistent and appropriately hedged: LLM extraction (e.g., Firecrawl/Apify "extract" endpoints that take a page + natural-language schema and return structured JSON) is genuinely more resilient to layout changes than CSS-selector scraping, but it costs more per page, is slower, and is explicitly *not* recommended as the primary mechanism for a "runs daily, feeds a database" durable pipeline — the recommended pattern is to use LLM extraction for discovery/prototyping or as a fallback when selectors break, then lock in tested selector-based extraction for the steady-state job. Worth keeping in your back pocket as the self-healing fallback for the HTML-scraping source specifically (detect selector breakage via your schema-drift check, fall back to LLM extraction, alert either way), not as the default extraction path.
- **Dagster+'s pricing change (May 2026, removing solo-tier credits)** is itself a "changed since mid-2026" data point worth flagging even though it doesn't change the recommendation — it's a concrete reason (beyond conceptual overhead) that the orchestration answer for solo projects has moved further toward cron/Prefect-OSS/GitHub-Actions, not toward Dagster, over the course of 2026.
- Nothing found suggests the medallion architecture, hexagonal ports-and-adapters framing, or the transactional-outbox pattern for a status state machine have been supplanted or gone out of favor — these remain current standard practice with no meaningful 2026 alternative displacing them for this scale.
