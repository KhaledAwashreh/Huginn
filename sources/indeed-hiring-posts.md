# Indeed — Job Postings

Verified live on 2026-09-05: `robots.txt` fetched directly, `indeed.com/legal` (Terms of Service, "Last Updated: July 17, 2026") fetched and parsed, `docs.indeed.com` fetched directly (returned a live Cloudflare CAPTCHA challenge — see below), plus web search against current (2026) third-party reporting on the Publisher API/Job Sync API status.

## Access

**No public read/search API exists.** This is the central fact for Bronze design.

- **Publisher Program / XML feed (historical)** — Indeed used to run a free, self-serve "Publisher" program: register, get a numeric publisher ID, call an XML endpoint with `q`/`l` (query/location) params, get job results back as XML for display on a partner's own site. **This program stopped accepting new members in 2022 and the Publisher API itself was shut down in 2023.** Existing publisher keys stopped returning data at that point. There is no current reopening, no public rate card, and no self-serve replacement.
- **What replaced it is not a data-access product** — it's an embeddable **iframe widget** (`publisher.indeed.com`) that displays Indeed's own search UI on a partner page; it gives no underlying data access at all.
- **Current official APIs are all write-side, employer/ATS-facing**, documented at `docs.indeed.com` (see caveat below) and referenced by third-party API cataloguers (e.g. the `api-evangelist/indeed` GitHub summary): a **Job Sync API** (GraphQL) lets ATS/staffing partners create, upsert, expire, and check status of **their own** job postings *on* Indeed, plus applicant/candidate-management and sponsored-jobs-spend APIs. None of these are designed to read or search listings that other employers posted — Job Sync is described in Indeed's own partner docs as pushing jobs *into* Indeed, not pulling jobs *out*. A "deprecated job search API" is explicitly noted as **not available for new integrations**.
- **Access path for these APIs is sales-led, not self-serve.** Indeed's partner model requires becoming an approved "Indeed partner," at which point Indeed provisions OAuth app credentials (client ID/secret, 3-legged OAuth) in a Partner Console. There is no self-serve signup form and no API key an individual can request — approval is aimed at established ATS/staffing-platform vendors, not individual developers or small projects. Third-party writeups describing attempts to get read-side access describe the enterprise partnership route as NDA-gated with reported six-figure minimums; that specific figure is unverified (single secondary source, not from Indeed itself) but is directionally consistent with everything else found here: **there is no economically realistic API path for a solo project.**
- **`robots.txt`** (fetched directly from `https://www.indeed.com/robots.txt` on 2026-09-05) is unusually detailed and user-agent-differentiated:
  - For the default `User-agent: *` group and the named-search-engine group (Googlebot, Bingbot, and a long list of AI-assistant crawlers like `Claude-User`, `PerplexityBot`, `OAI-SearchBot`): search-result pagination is `Allow`ed only up to `start=90` (deeper pagination is `Disallow`ed), and **individual job-detail pages are blocked** (`Disallow: /viewjob?`, `Disallow: /job/`, `Disallow: /Job/`, plus per-country `Disallow: /jobs/US/`, `/jobs/CA/`, `/jobs/GB/`, etc., and `Disallow: /jobs/title`). Company profile pages are also blocked (`Disallow: /company/*`).
  - A **separate, explicit blanket-block group** singles out known scraping tools and job-data aggregators by name and gives them `Disallow: /` (everything): `Scrapy` (the default User-Agent string of the most common Python scraping framework), `ia_archiver`, `omgili`/`omgilibot`/`Webzio`/`Webzio-Extended` (a commercial web-data reseller), `JobdiggerSpider` (a job-aggregator crawler), `Cliqzbot`, `GoogleOther`, `MyCentralAIScraperBot`. This is a direct, named signal that Indeed actively tracks and blocks generic/default scraper identities, not just unnamed bots.
  - A **fourth group for AI-training crawlers** (`GPTBot`, `CCBot`, `anthropic-ai`, `ClaudeBot`, `DeepSeekBot`, `GrokBot`, `Diffbot`, `Bytespider`, `AmazonBot`, `Applebot-Extended`, etc.) is disallowed from essentially all job and company content outright: bare `Disallow: /jobs`, `Disallow: /viewjob`, `Disallow: /companies/`, `Disallow: /cmp/`, `Disallow: /career/`, `Disallow: /career-advice/`. This group is *more* restricted than the plain search-engine group above — Indeed is explicitly walling off job/company content from AI crawlers specifically, on top of the general scraper block.
  - Net effect: **there is no robots.txt-sanctioned path to individual job postings for any automated agent**, regardless of which honest user-agent string it identifies as. The only thing arguably in-bounds for a generic bot is a shallow, first-9-pages-only crawl of search-result listing pages — not the postings themselves.
- **Terms of Service** (`indeed.com/legal`, "Last Updated: July 17, 2026") contains an explicit, on-point clause (quoted verbatim, prohibitions section):
  > "Use any automated system (bots, scrapers, spiders, AI or Agentic AI) to access, data-mine, or submit content to the Site, in bulk or otherwise, without Indeed's express written permission (we conditionally grant permission to crawl the Site solely as outlined in our robots.txt file). You may not crawl, scrape, extract data from, reproduce, duplicate, copy, sell, exploit, trade or resell any part of the Site or access the Site for the development, training, fine-tuning, or improvement of any third-party machine learning model, artificial intelligence (AI) system, or any related software program, model, algorithm, or generative AI tool[.]"

  This ties permission directly and explicitly back to `robots.txt` ("solely as outlined in our robots.txt file") — i.e. Indeed has drafted its ToS so that a `robots.txt` violation is *also* a ToS violation, closing the "robots.txt is only a voluntary convention" argument that courts have sometimes credited in other scraping disputes (see Open questions/risks). The Terms also give Indeed unilateral termination rights ("Indeed may, at its sole discretion, suspend or terminate your account... or restrict, suspend or terminate your access to any part of the Site, at any time, for any or no reason, without prior notice or liability").
- **Live enforcement, confirmed empirically today, not just in the ToS text**: a plain `curl` with a standard desktop Chrome `User-Agent` string against `docs.indeed.com` (Indeed's own partner-docs subdomain) returned an **HTTP 403 Cloudflare "Security Check" / managed CAPTCHA challenge page** (`window.INDEED_CLOUDFLARE_STATIC_PAGE={PAGE_TYPE:"captcha", RAY_ID:"a36489795bdde167"}`, page title "Security Check - Indeed.com", body text "Additional Verification Required... Please enable JavaScript to complete the security check."). This happened on the **documentation** site, not even a job-search page — it's evidence Cloudflare bot-management is active site-wide, at low request volume, against a single unauthenticated request with a normal browser UA and no prior request history. Real job-search pages, which are far higher-value to protect, should be assumed to be at least as aggressively gated (third-party scraping-vendor blog posts from 2026, e.g. ScrapeOps/Bright Data/ScrapFly writeups on scraping Indeed, corroborate Cloudflare-backed protection with device-fingerprinting-grade challenges as the current state, consistent with what was just observed directly).
- **Bottom line on access**: no API, no feed, no publisher program open to new entrants, and both the written ToS and the live infrastructure actively work against unauthorized automated access to exactly the pages Huginn would need (individual job postings). There is no "gray legitimate" path here the way there arguably is for e.g. HN's unauthenticated-but-permissive API — this is a source that has been deliberately locked down.

## Response shape

No structured access exists, so this section is necessarily hypothetical/historical rather than fetched-and-confirmed, unlike the other sourced docs in this folder.

- **Old Publisher API (defunct since 2023)**: accepted `q` (query) and `l` (location) plus paging params, returned XML. Secondary sources describing it don't specify a complete field list, but it's consistent with what every job-aggregator API of that era exposed: job title, company name, location (city/state/country, sometimes lat/long), a snippet/summary of the description (not full text), a `date` (posting date, relative or ISO), a `url` (link back to the Indeed-hosted job page, not necessarily the employer's own domain), and a unique job key (`jk` parameter, the same one visible in `viewjob?jk=...` URLs today). Salary was **not** a standard Publisher API field historically — Indeed's own salary estimates/employer-provided salary ranges are a newer UI feature layered onto the web pages, not something the old XML feed reliably carried.
- **What the live web pages themselves carry (not fetchable without violating robots.txt/ToS, so not verified here, but standard practice for job boards for SEO purposes)**: individual job pages on Indeed and most job boards embed `schema.org/JobPosting` JSON-LD structured data (used by Google for Jobs) which would include `title`, `hiringOrganization` (company name, sometimes `sameAs`/logo but rarely a direct company-domain field — Indeed's own job pages typically link to Indeed's internal `/cmp/<company-slug>` company profile, not the employer's real website), `jobLocation`, `datePosted`, `validThrough`, `description` (full HTML), and `baseSalary` (present when Indeed has an estimate or the employer supplied a range). This is *inferred from how the format is generally used on job boards*, not confirmed against a live Indeed page in this research pass — company-profile pages (`/cmp/*`) and individual job pages (`/viewjob`, `/job/`) are both explicitly `Disallow`ed in `robots.txt`, so pulling one to verify would itself be the kind of access this document is evaluating as non-viable.
- **Company URL/domain**: even when present, Indeed's own UX generally routes to Indeed's internal company profile rather than the employer's real domain — this is the same "which link is canonical" ambiguity noted in the HN Who's Hiring and Ramp docs in this folder, but worse here because Indeed has a commercial incentive to keep traffic on-platform (drive to its own `/cmp/` pages) rather than surface the employer's own site.

## Freshness / cadence

- Indeed is one of the largest job boards globally; new postings from any given company can appear at any time, with no predictable schedule (unlike HN's monthly thread or a newsletter's fixed cadence).
- **No officially supported "since X" / delta-polling mechanism exists** for third parties. The old Publisher API had no webhook or changed-since parameter documented in what's findable now (it's fully shut down, so this can't be verified against live docs either way). The current Job Sync API's "get status" capability is scoped to jobs *the calling ATS partner itself posted* — not a general "what's new across Indeed" feed.
- The only way to detect "did company X post a new job" without partner access would be **repeated polling/scraping of search-result or company pages on a schedule Huginn controls** — which is exactly the activity `robots.txt` and the ToS both target, and exactly what triggered a live CAPTCHA challenge in this research pass against a single low-volume request to a documentation subdomain.
- Practically: any workable cadence would require either (a) an approved enterprise/ATS partnership (sales-led, not available to a solo project per above), or (b) unauthorized scraping through anti-bot infrastructure, which has real ongoing operating cost (proxy rotation, headless-browser fingerprint management, CAPTCHA-solving services) on top of the legal exposure — not a one-time integration cost like the other sources in this folder.

## Open questions / risks

**Direct answer to "is this realistically usable": no — this source should be marked not realistically viable for a solo/small project, full stop, not just "viable with caveats."** The other 8 sources in this folder each have at least one clean, low-risk access path (an open unauthenticated API, a self-serve directory scrape of a page that isn't actively fighting bots, or a documented partner feed). Indeed has none of these:

- **No API tier exists between "nothing" and "enterprise sales deal."** Unlike LinkedIn (which at least has a partner-tier "Talent Solutions" ecosystem some legitimate small integrators have accessed, however imperfectly) or even Ramp/HN (open access, no gate at all), Indeed's Publisher self-serve program — the one thing that used to fit a solo project's scale — was deliberately shut down in 2023, specifically (per Indeed's own stated rationale, reported secondhand) because open feeds "helped competitors and aggregators build products on Indeed's inventory without sending traffic back." That's a considered business decision to close the exact gap Huginn would need, not an oversight or a temporary gap.
- **The ToS clause is unusually well-drafted against exactly this use case.** It doesn't just say "no scraping" generically — it explicitly names "AI or Agentic AI," explicitly forbids use "for the development, training, fine-tuning, or improvement of any third-party machine learning model... or any related software program, model, algorithm," and explicitly ties permitted crawling back to `robots.txt` compliance. An LLM-agent-based ingestion pipeline (which is effectively what a Huginn Bronze ingester assisted by an AI coding agent is) sits squarely inside language this ToS was clearly updated (within the last two months, per the July 17, 2026 "Last Updated" date) to cover.
- **This is directly analogous to the hiQ v. LinkedIn fact pattern the user asked about, but with the opposite outcome so far.** hiQ succeeded (at the preliminary-injunction stage, under the CFAA specifically) partly because LinkedIn's public profile pages had no robots.txt-level or technical access control at all at the time, and the Ninth Circuit's reasoning leaned on scraping *publicly accessible* data not being "without authorization" under the CFAA. Indeed's setup is meaningfully different: (a) `robots.txt` **does** explicitly restrict the exact pages at issue (individual job postings) for generic/AI bots, and the ToS explicitly makes that restriction contractual, not just a voluntary signal; (b) live technical enforcement (Cloudflare managed challenge, confirmed live today even against a low-volume single request) is actually in place, unlike a site with no active bot-blocking. Both of the factors most favorable to hiQ's side of that precedent point the other way for Indeed. No specific Indeed-v-scraper lawsuit was found in this research pass (a targeted search turned up general commentary that Indeed "actively sends cease-and-desist letters to scrapers that redistribute their data," but no named case) — the risk here isn't "there's a known Indeed lawsuit to point to," it's that Indeed has pre-built every structural element (technical block + explicit contractual block + a track record of shutting down open access on purpose) that plaintiffs in *other* scraping cases had to piece together after the fact.
- **Even setting aside legal risk, the operating-cost risk alone likely kills this for a solo project.** Anti-bot infrastructure at Indeed's level (Cloudflare managed challenge/CAPTCHA, likely device-fingerprint-based escalation on repeat requests) means a workable scraper isn't a weekend script — it's an ongoing arms race requiring residential-proxy rotation, headless-browser fingerprint spoofing, and/or third-party CAPTCHA-solving services, each with real recurring dollar cost and each individually a fragile dependency that can break on any Indeed-side change. That's a fundamentally different cost profile than every other source in this folder.
- **Recommendation**: do not build Indeed ingestion. If hiring-signal coverage from a major aggregator is still wanted, the more defensible options are (a) staying with HN Who's Hiring / YC / VC portfolio boards / newsletters, all already in this folder and all either fully open or at least not contractually and technically hardened against exactly this use case, or (b) if broader job-board coverage is truly needed later, budgeting for a paid third-party jobs-data API (e.g. the "unified jobs API" vendors that surfaced in this research, such as JobsPipe, TheirStack, Coresignal, Bright Data's Indeed scraper product) that has presumably already priced in Indeed's enforcement risk into its own commercial terms — that shifts the compliance/technical burden to a vendor for a fee, rather than Huginn taking it on directly. That tradeoff (cost vs. building/maintaining your own scraper against active anti-bot defense) should be made explicitly and separately, not by defaulting into direct scraping.
